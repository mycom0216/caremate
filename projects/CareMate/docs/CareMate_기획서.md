# CareMate 프로젝트 기획서

인공지능 응용 시스템 개발 종합 프로젝트 · 작성일 2026-11-20 · 작성자 반재영 (개인 프로젝트)

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | CareMate — RAG 챗봇 기반 고객 문의 분석·상담 지원 시스템 |
| 한 줄 요약 | 고객 문의에 안내 문서를 근거로 답하고, 답할 수 없거나 급한 문의는 분석해 상담원에게 넘기는 시스템 |
| 대상 도메인 | 가상의 온라인 쇼핑몰 '모아마켓' (실제 기업·데이터 아님, 직접 작성한 안내 문서 37개 항목) |
| 핵심 AI 기술 | RAG(검색 증강 생성) 챗봇, 로컬 LLM(Ollama + kanana2:3b), 나이브 베이즈 문의 분류, 사전 기반 감정·긴급도 분석 |
| 개발 환경 | Node.js 24+, SQLite(node:sqlite), HTML/CSS/JavaScript. 외부 npm 패키지 없음 |

## 2. 개발 배경과 목적

쇼핑몰 고객센터 문의의 상당수는 배송비, 반품 기간, 쿠폰 사용 규칙처럼 이미 안내 문서에 답이 있는 반복 질문입니다. 상담원이 같은 답을 반복해서 작성하는 동안 결제 오류나 파손처럼 빨리 처리해야 하는 문의가 뒤로 밀릴 수 있습니다.
일반 챗봇(LLM)만 붙이면 문서에 없는 정책을 그럴듯하게 지어내는 문제(환각)가 생기고, 잘못된 환불·반품 안내는 곧바로 고객 불만으로 이어집니다.

**목표**
1. 안내 문서에 있는 내용은 **출처와 함께** 정확히 답한다 (RAG).
2. 문서에 근거가 없으면 지어내지 않고 **상담원에게 넘긴다** (환각 방지 + 에스컬레이션).
3. 모든 문의를 **유형·감정·우선순위로 자동 분석**해 급한 문의를 먼저 처리하게 한다.
4. 상담원에게는 근거가 달린 **답변 초안**을 제공해 작성 시간을 줄인다.
5. 운영자에게는 **대시보드**로 어떤 주제가 많이 문의되는지 보여 준다.

## 3. 요구사항 분석

### 3.1 사용자와 시나리오
| 사용자 | 하고 싶은 일 |
|---|---|
| 고객 | 24시간 즉시 답을 얻고, 주문번호로 배송 상태를 확인하고, 필요하면 사람 상담원과 연결 |
| 상담원 | 챗봇이 못 푼 문의를 우선순위순으로 보고, 근거가 달린 초안을 검토·수정해 답변 |
| 운영자 | 문의 유형 분포, 자동 해결률, 고객 만족도, 자주 묻는 주제를 확인해 안내 문서를 개선 |

### 3.2 기능 요구사항
| ID | 기능 | 완료 기준 |
|---|---|---|
| F1 | 문서 기반 답변(RAG) | 답변과 함께 근거 문서 ID·원문 표시 |
| F2 | 근거 부족 처리 | 근거가 없으면 답변을 지어내지 않고 티켓 생성 |
| F3 | 환각 방지 검사 | 답변의 숫자·근거 일치도 검사, 실패 시 폐기 또는 원문 발췌 |
| F4 | 주문 조회 | `MM-1001` 형식 주문번호로 DB의 실제 상태 답변 |
| F5 | 문의 분석 | 유형 분류, 감정 점수, 우선순위(근거 단어 포함) |
| F6 | 개인정보 보호 | 전화·이메일·카드·주민번호 마스킹 후 저장 |
| F7 | 상담원 콘솔 | 우선순위순 티켓 목록, AI 답변 초안, 답변 등록(중복 처리 방지) |
| F8 | 대시보드 | 총 문의, 자동 해결률, 평균 응답시간, 만족도, 유형별·인용 지식별 통계 |
| F9 | 맥락 이어가기 | "그럼 배송비는요?" 같은 짧은 후속 질문 처리 |
| F10 | 고객 피드백 | 답변별 👍/👎 저장 |

### 3.3 비기능 요구사항
- LLM 서버가 없어도 동작(추출형 답변으로 자동 대체).
- 입력 500자 제한, 요청 속도 제한, 응답의 XSS 방지(textContent 사용).
- 모바일 폭(375px)에서 가로 스크롤 없음.
- 개인정보는 저장 전에 마스킹하고, 챗봇 화면에 입력 금지 안내를 표시.

## 4. 시스템 설계

### 4.1 아키텍처

```
고객/상담원/운영자 (브라우저)
        │  REST API (JSON)
        ▼
  Node.js 서버 ── ChatService ─┬─ ① PII 마스킹 → ② 문의 분석(분류·감정·우선순위)
        │                      ├─ ③ 분기: 상담원 요청 / 잡담 / 주문번호 조회 / RAG
        │                      ├─ ④ Retriever: BM25(문자 바이그램) [+ 임베딩 선택]
        │                      ├─ ⑤ LLM(Ollama kanana2:3b) 생성 → ⑥ 환각 방지 검사
        │                      └─ ⑦ 실패 시 추출형 답변 또는 상담원 티켓
        ▼
  SQLite: orders · inquiries · tickets          knowledge/*.md (37개 항목)
```

### 4.2 RAG 파이프라인
1. **색인**: `knowledge/*.md`를 `## [ID] 제목` 단위로 분할 → 문자 바이그램 토큰으로 BM25 색인.
2. **검색**: 질문에서 군말("알려줘", "어때")을 제거하고 BM25 점수로 상위 4개 선택. 질문 토큰의 가중 커버리지와 코퍼스 밖 어절 비율로 **신뢰도**를 계산.
3. **분기**: 신뢰도가 임계값(0.2) 미만이면 답변하지 않고 상담원 티켓 생성.
4. **생성**: 상위 4개 문서만 프롬프트에 넣고 "문서에 없으면 '근거 부족'이라고만 답하라"고 지시.
5. **검증**: (a) 답변의 숫자가 문서·질문에 있는지, (b) 인용 번호 범위, (c) 답변 바이그램의 문서 일치도 ≥ 0.5. 실패하면 검색 신뢰도가 높을 때만 원문 발췌로 대체하고, 아니면 상담원에게 넘김.

### 4.3 데이터 설계
| 테이블 | 주요 컬럼 |
|---|---|
| orders | order_no(PK), item, amount, status, carrier, tracking_no, eta |
| inquiries | id, session_id, question(마스킹됨), category, category_prob, sentiment, priority, reasons, answer, generator, confidence, sources, escalated, latency_ms, feedback |
| tickets | id, inquiry_id(FK), reason, priority, status(open/resolved), reply, replied_at |

티켓 답변은 `WHERE status='open'` 조건의 단일 UPDATE로 처리해 중복 답변·동시 처리를 막습니다.

### 4.4 API
`POST /api/chat`, `GET /api/inquiries`, `GET /api/stats`, `GET /api/tickets`, `GET /api/tickets/:id/draft`, `POST /api/tickets/:id/reply`, `POST /api/inquiries/:id/feedback`, `GET /api/kb`, `GET /api/kb/search`, `GET /api/status`.

## 6. 평가 계획
- **검색 평가**: 정답 문서가 정해진 질문 38개 → hit@1, hit@4.
- **범위 밖 질문**: 날씨·주식 등 5개 → 거절(상담원 연결) 여부.
- **답변 평가**: 핵심 사실 문구 포함 여부(자동) + 개발자 수기 검토.
- **분류 평가**: 학습과 분리된 24문장 정확도.
- **응답 시간**: 질문별 응답 시간의 중앙값과 최댓값.
- **단위·통합 테스트**: 30개 자동 테스트.
- 평가 질문은 개발자가 직접 작성하므로 실제 고객 질문 분포와 다를 수 있음을 결과보고서에 명시한다.
